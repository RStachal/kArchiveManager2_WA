Problém

Produkční WMS databáze rostou donekonečna

  • Logy, doklady, integrační fronty se nikdy nemažou → tabulky mají miliony až stovky milionů řádků.
  • Důsledek: pomalejší dotazy, delší zálohy, dražší úložiště, riziko provozních výpadků.
  • Ruční mazání je nebezpečné — co když smažu něco, co ještě potřebuju? A kde to pak vezmu?
Jádro problému Stará data je potřeba dostat z produkce pryč — ale bezpečně, dohledatelně a bez zásahu do běžícího provozu.

kArchive Manager 2.0 v jedné větě

Automaticky a bezpečně archivuje a maže stará data z produkčních databází: staré řádky nejdřív zkopíruje do archivní databáze a teprve pak je z produkce smaže.

staré řádky → archiv → smazat z produkce

01 · Proč03
Přínosy pro zákazníka

Co tím zákazník získá

Výkon

Štíhlá produkce = rychlejší WMS, kratší zálohy, nižší náklady na úložiště.

Nic se neztratí

Smazané řádky jsou vždy nejdřív v archivu (FULL recovery + zálohy). Lze je dohledat i vrátit.

Auditovatelné

O každém smazaném dokladu je neměnný záznam — kdo/co/kdy. Splní compliance.

Bezpečné z principu

Mazání je dávkové, transakční a hlídané branami; výběr dat nezamyká produkci.

Univerzální

Konfigurace, ne kód. Nové tabulky/DB se přidají nastavením, ne programováním.

Pod kontrolou

Webová Admin Console + plánované noční joby + reporty a odhady dopadů.

Dvě databáze nástroje — co v nich je

  • Konfigurace: procesy, mapování, retence, režimy
  • Historie běhů: Run / RunItem (co/kdy/kolik/stav)

3 · Kontrola
archivováno == smazáno
Divergence = 0
  • Mazání je jeden příkaz DELETE … OUTPUT INTO archiv — řádek se ve stejné transakci zazálohuje i smaže.
  • Nikdy tedy nenastane stav „smazáno, ale nezálohováno". U režimu 1 platí archivováno == smazáno.
Věta pro zákazníka „Mode 1 → Divergence = 0. Když by se nemělo co bezpečně smazat, nesmaže se nic."
03 · Mechanismy10
Retence a cutoff

Dotkne se jen dat starších než hranice

staré / způsobilé k archivaci
cutoff (hranice)
mladé / NEDOTČENO
  • Retence / cutoff = stáří, za kterým je řádek „způsobilý". Mladší data se nikdy nedotknou.
  • Retenční podlaha (brána 50210) — nikdo nemůže nastavit retenci pod bezpečné minimum.
  • Legal hold — vyjmenované doklady se nikdy nearchivují (právní pozdržení).
Pozor — časová zóna Data porovnáváme v UTC. Špatně nastavená zóna zdroje = brána 50200. Proto se cutoff počítá konzistentně přes AT TIME ZONE.
03 · Mechanismy11
Strategie & režimy

Dva způsoby výběru, tři režimy

Strategie výběru

  • ANCHOR — doklad + jeho řádky jako celek (RECEIVING, SHIPPING). Dvoufázově: PREP připraví, RUN spustí.
  • TIMESTAMP — záznamy podle času (logy, RF_LOG2). Jednofázově podle klíče.

Režim (Mode)

  • 1 — archivovat + smazat (běžné). Divergence = 0.
  • 0 — jen smazat (vyžaduje explicitní povolení).
  • 2 — jen kopírovat (idempotentní záloha, bez mazání).
Pro podporu Nemusíš znát detail ANCHOR vs TIMESTAMP — stačí „dva způsoby výběru podle typu dat". Důležité je vědět, že Mode 0/2 se chovají jinak (Mode 2 nemaže → Divergence ≠ 0 je tam normální).
03 · Mechanismy12
Klíčový provozní princip

Výběr dat nezamyká produkci

PREP — výběr kandidátů

Čte zdroj přes NOLOCK (read uncommitted) → bere nula datových zámků. Běží kdykoli, i mimo okno.

drží jen Sch-S → nikdy neblokuje OLTP

RUN — mazání (DELETE)

Bere zámky jen na mazané řádky, v dohodnutém nočním okně, v malých dávkách (< 5000 řádků → bez eskalace na zámek tabulky).

u multi-index tabulek: LOCK_ESCALATION = DISABLE

Proč to zákazníka zajímá Archivace neblokuje běžící WMS. Bezpečné je to z principu — výběr nezamyká, mazání je drobné a v okně. Žádné indexy se ve zdroji nezakládají.
03 · Mechanismy13
Auditovatelnost

O každém smazaném dokladu je neměnný záznam

  • RunDocAudit — per doklad: klíč, kdy vytvořen, kdy smazán, zda archivován.
  • RunItemObject — počty per zdrojová tabulka; Run/RunItem — kdo/kdy/stav běhu.
  • Audit je neměnný (DENY UPDATE/DELETE) — nelze ho zpětně přepsat ani smazat.
  • Úroveň auditu: NONE / BATCH / ROW (kompromis výkon × stopa).
Typický dotaz „Byl tenhle doklad smazán a kde je?" → Document lookup v Console (čte z auditu + archivu). Žádné šťourání v produkci.

Analysis & Estimates — všechny procesy, scroll, odhady

Co grafy ukazují

  • Všechny procesy a tabulky (dřív skrytý RF/L filtr je pryč) — Source vs Archived, denní přenosy, podle cutoffu.
  • Dlouhé seznamy se scrollují uvnitř panelu (nestahují stránku donekonečna).
  • KPI dlaždice: mapped tables, source/archived rows, runs.

Odhady další dávky (opt-in)

  • L1 čte: „kolik se bude příště mazat".
05 · Console21
Console · Konfigurace

Process = výchozí, Mapping = override

Hodnota nastavená na mapování (Source→Archive DB) přebíjí stejnou hodnotu na procesu. Runtime bere COALESCE(mapping, process).

Co je nově vidět

  • Sloupec „Overrides" v Database mappings — vypíše, která pole mapping přebíjí (např. Mode, Audit, BatchRows).
  • Badge u zdroje: amber = přebito na mappingu, neutrální = zděděno z procesu.
  • Editor procesu varuje: „toto jsou výchozí hodnoty; mapping je může přebít".

Past, které se vyhnout

  • Změna na procesu se neprojeví, pokud ji mapping přebíjí.
  • Chceš-li změnit reálně použitou hodnotu → edituj mapování (viz Overrides).
05 · Console22
Console · Konfigurace

Cutoff (UTC + lokální náhled), audit, režimy

Cutoff

  • Relativní retence (dní) — bez TZ nejasností (doporučeno).
  • Pevné datum = 00:00 UTC; editor živě ukáže lokální hranici (zima +1 h, léto +2 h).

Audit

  • NONE / BATCH / OBJECT / ROW (per doklad).
  • Plný ROW audit stojí ~21 % výkonu — volitelně per mapping.

Režimy

  • 1 archiv+smaz · 0 jen smaz · 2 jen kopie
  • Copy-only je idempotentní (2. běh nic nezduplikuje).
Tip Velikost archivu je hlavní faktor rychlosti — viz archive-performance-tuning.md (parking indexů, dávkování, partitioning).

Odemčení editace

05 · Console24
Proč tomu věřit

Provozní záruky — ověřené testy

Konzistence dat

  • Divergence = 0 — smazáno == archivováno (atomická dávka), ověřeno na ~5 M řádcích.
  • Crash uprostřed běhu nic neztratí ani nezduplikuje (rozdělaná dávka se rollbackne); RecoverStaleRuns uklidí, zbytek je resumovatelný.

Bezpečnost provozu

  • Výběr nezamyká produkci (NOLOCK, 0 eskalací); žádné indexy ve zdroji.
  • Souběh: applock serializuje dva běhy (žádné dvojí archivování).
  • Retenční podlaha (50210) a legal-hold brání smazání chráněných dat.

Chybové kódy — první reakce

Co uvidíš v historii jobu

51001
Runner nemá oprávnění(běží jako sysadmin/Agent). Časté po obnově/redeployi DB! → L2: 053+054 (+ MULTI_USER).
51000
Konfigurace není platná (např. chybí zdrojová DB). → L2: Validation / Configuration.
50200
Časová zóna není správně. → L2: ověřit TZ procesu.
50210
Retence pod minimum — odmítnuto správně (retenční podlaha).
50115/116
Klíč není unikátní / souběh — dva běhy najednou nebo špatný klíč.
50400
Nebezpečný SQL výraz v konfiguraci (safe-expr brána).
50223
Copy-only bez PK — tabulka potřebuje primární klíč.
50500+
Chyba odhadu (Estimates) — většinou neškodné, zkusit znovu.
06 · Chyby27
Incident č. 1 — musíš znát

Po obnově / redeployi DB padají joby na 51001

Co se stalo: obnova zdrojové/archivní DB nebo přenasazení bundlu smaže runner granty a vrátí vlastníka jobu na sysadmina → běh jede pod Agent účtem → brána T-33 ho odmítne.

  • Příznak v logu: Executed as user: NT SERVICE\SQLAgent$… (Error 51001)
  • Často i 51000 (re-seed zapnul mapping na DB, která byla dropnutá).
Fix (L2)
  1. znovu spustit 053 + 054 (granty + přeovnění jobů na runner účet)
  2. případně SET MULTI_USER na obnovené DB
  3. sladit zapnuté mappingy s reálně existujícími DB

Bezpečnostní model

Vrstvy ochrany

Role (RBAC)

viewer / operator / config_admin / approver / runtime — každý vidí a smí jen své.

Least-priv runner

Noční joby běží pod non-sysadmin účtem s minimem práv (brána 51001 sysadmina odmítne).

Neměnný audit

DENY UPDATE/DELETE — stopu smazání nelze přepsat.

Elevated tier

Restore do produkce vyžaduje vyšší (jmenovité) oprávnění; sdílené heslo nikdy.

4-eyes + důvod

Každá změna konfigurace = důvod + audit (kdo/kdy/co).

Brány při běhu

TZ (50200), retence (50210), safe-expr (50400), souběh (50116).
