# Performance Benchmark — kArchiveManager 2.0 (release blocker R-03)

**Date:** 2026-06-18 · **Harness:** `tools/r03_benchmark/` · **Applies to:** v2.0.0

This document defines the **performance benchmark** required to clear release condition **R-03**:
a repeatable measurement of the runner chain at customer scale, capturing full engine metrics
with correct attribution, evaluated against explicit **acceptance criteria**.

Companion (always-true safety facts, not perf): `docs/v2-performance-best-practices.md`,
`docs/audit-model.md`. Compatibility scope: `docs/COMPATIBILITY-MATRIX.md`.

---

## 1. What the harness measures (and how it attributes)

The harness wraps a single execution of `arch.usp_RunConfiguredProcesses_Prepared` (the same proc
the SQL Agent jobs call) and snapshots before/after. Because the runner executes on the **caller's
session**, per-session counters attribute the whole run cleanly.

| Metric | Source | Attribution |
|---|---|---|
| Elapsed (ms) | `SYSUTCDATETIME()` around the `EXEC` | exact |
| CPU (ms) | `sys.dm_exec_sessions.cpu_time` delta on `@@SPID` | per-session |
| Logical reads | `sys.dm_exec_sessions.logical_reads` delta | per-session |
| Physical reads | `sys.dm_exec_sessions.reads` delta | per-session |
| Writes | `sys.dm_exec_sessions.writes` delta | per-session |
| tempdb (KB) | `sys.dm_db_session_space_usage` (user+internal alloc pages × 8) delta | per-session |
| **Log bytes / DB** | `sys.dm_os_performance_counters` `Log Bytes Flushed/sec` (cumulative) delta, per DB (source + archive) | per-DB, window |
| Log free at start | `DBCC SQLPERF(LOGSPACE)` | per-DB, point-in-time |
| Lock waits (ms) | `sys.dm_os_wait_stats` `LCK_M_*` delta | instance, window |
| Deadlocks | XE `xml_deadlock_report` count | window |
| **Lock escalation (source)** | XE `lock_escalation` filtered `database_id = DB_ID(source)` | window |
| Sort / hash spills | XE `sort_warning` / `hash_warning` count | window |
| Rows archived/deleted, divergence, bad items | `arch.RunItem` for runs created in the window | exact (product telemetry) |

> **⚠️ Isolation requirement.** Log-bytes, lock-wait, and XE counts are *instance/DB-window*
> measurements. Run the benchmark on an **otherwise-idle instance** (no concurrent writers on the
> source/archive DBs). Per-session metrics (CPU, reads, tempdb) stay accurate regardless. This is
> also why the benchmark belongs on a TEST/staging copy, not a busy production instance.

Why these choices (rejected alternatives): `SET STATISTICS IO/TIME` is per-statement and cannot be
aggregated across a multi-batch proc; `dm_exec_query_stats`/`procedure_stats` aggregate across all
callers and suffer plan eviction; `dm_db_log_space_usage` reports *current* log size (polluted by
checkpoint/truncation) rather than *bytes generated*. The session-delta + cumulative-perf-counter
model gives the cleanest "this run" attribution.

## 2. Scale matrix

Pick `@MaxCandidates` per scale (the runner caps candidates), keeping `BatchRowCount` at the
configured production value so escalation/log behaviour is representative. Run every row that
applies to the customer (both strategies, the modes in use, cheap-mode where configured).

| Scale | Rows (`@MaxCandidates`) | Purpose |
|---|---|---|
| small | 10 000 | smoke / correctness; fast feedback |
| medium | 200 000 | steady-state batch behaviour |
| large | 1 000 000 | sustained throughput + log/tempdb pressure |
| prod-rep | a realistic daily/cutover volume for the customer (e.g. 5–10 M) | go-live sizing |

Dimensions to cover: **ANCHOR** and **TIMESTAMP**; **Mode 1** (archive+delete) primarily, plus
**Mode 0** / **Mode 2** if the customer uses them; **cheap-mode on/off** for high-volume TIMESTAMP
sources. Run each scenario at least twice (warm cache) and keep the median.

## 3. Acceptance criteria

Stored in `bench.AcceptanceThreshold` (tunable). A run is **PASS** only if **all** applicable gates
hold. `bench.usp_EvaluateAcceptance` records `Verdict` + `FailReasons` on each `bench.Run` row.

| Gate (threshold code) | Default | Rationale | FAIL surfaced as |
|---|---|---|---|
| `DIVERGENCE_MODE1` | `= 0` | Core invariant: every deleted row was archived first. | `Mode1 divergence=N` |
| `DEADLOCKS_MAX` | `= 0` | A correct batched run must not deadlock. | `Deadlocks=N` |
| `LOCK_ESCALATION_SOURCE_MAX` | `= 0` | Escalation to a table-X lock on the **source OLTP** table blocks the application. Keep `BatchRowCount` < 5000 (the engine escalation threshold). | `Source lock escalations=N` |
| `LOG_BUDGET_FRACTION` | `< 0.50` | Per DB, log generated by one run must stay below half the log **free** space at start, so a single run cannot fill the log. | `Source/Archive log M MB >= 0.5 x free` |
| `TEMPDB_MAX_MB` | `< 4096` | Detect runaway sort/hash spill. | `tempdb=N MB` |
| `ROWS_PER_SEC_MIN` | `>= 800` | Throughput floor. Measured baselines: ~1600–3000 rows/s (mode/audit dependent), ~3128 rows/s cheap-mode @100M. | `Throughput N rows/s < min` |
| `BAD_RUNITEMS_MAX` | `= 0` | No `arch.RunItem` ended FAILED. | `Bad RunItems=N` |

Tune a threshold:
```sql
UPDATE bench.AcceptanceThreshold SET NumericValue = 1500 WHERE Code = 'ROWS_PER_SEC_MIN';
```
Dry runs (`@DryRun = 1`) evaluate only concurrency/integrity gates (deadlocks, escalation, tempdb,
bad items); data gates (divergence, log budget, throughput) are skipped and the verdict is `DRYRUN`.

## 4. Operator runbook

Prereqs: an idle TEST/staging instance with a representative data copy; the connecting login has
`VIEW SERVER STATE`, `ALTER ANY EVENT SESSION`, and `EXECUTE` on the runner chain.

**Option A — PowerShell (Windows auth, captures to `publish/`):**
```powershell
cd tools/r03_benchmark
./r03_run.ps1 -ServerInstance "RADIM-STACHAL\RSTSQL2022" `
              -ProcessCode RF_LOG2 -SourceDb Edge -ScaleLabel large `
              -Strategy TIMESTAMP -CheapMode -MaxCandidates 1000000
```

**Option B — SSMS / sqlcmd:**
1. Run `tools/r03_benchmark/r03_benchmark_harness.sql` once (installs `bench` schema + XE session).
2. Edit and run section A of `tools/r03_benchmark/r03_run.sql` for a single scenario, or uncomment
   section B for a full matrix sweep across all enabled mappings.
3. `EXEC bench.usp_BenchmarkReport;` for the results.

Between scales, **restore the source/archive DBs** (or use a fresh copy) so each run starts from a
known volume — the same discipline as `tools/_retest_sweep.sql`.

## 5. Interpreting results

- `bench.vw_BenchmarkReport` gives a one-line-per-run summary (duration, rows/s, reads, tempdb MB,
  source/archive log MB vs free, deadlocks, source escalations, verdict).
- A FAIL on `LOG_BUDGET_FRACTION` ⇒ lower `BatchRowCount`/`MaxBatchesPerRun` or grow/back-up the log.
- A FAIL on `LOCK_ESCALATION_SOURCE_MAX` ⇒ lower `BatchRowCount` below 5000, or apply
  `ALTER TABLE … SET (LOCK_ESCALATION = DISABLE)` on the source table for the maintenance window.
- A FAIL on `ROWS_PER_SEC_MIN` for TIMESTAMP @ high volume ⇒ enable cheap-mode
  (`ObjectSpec.CandidateSelectExpr` + `ProcessDatabase.CandidateWhereSql`) and the source index.
- High tempdb / sort spills ⇒ check the candidate `OrderSql`/keyset vs the source index ordering.

### Limitations (honest)

- The harness measures; it does not size the hardware. Numbers are only representative if the data
  copy and `BatchRowCount` match production.
- Log/lock/XE metrics require instance isolation (§1). On a shared instance they over-count.
- XE ring-buffer spill counts can undercount under extreme spilling (memory cap); `TempdbAllocKB`
  is the quantitative spill measure, the XE counts are a presence/severity signal.
- This is the methodology and tooling. The **actual benchmark numbers at customer scale are
  NEOVĚŘENO until run on the customer environment** — that execution is the R-03 deliverable.
